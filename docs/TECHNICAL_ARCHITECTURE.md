# ארכיטקטורה טכנית מוצעת

**הערה:** זו הצעה ראשונית בלבד. בחירת הטכנולוגיות הסופית תלויה בספק נתוני התחבורה, בתקציב וביכולות הצוות.

**עדכון 16.10.2026:** המסמך עודכן לפי אפיון 2.0 (פרק 10) ולפי ההחלטות 10–14 ב־`planning/DECISIONS.md`: ספק הנתונים נבחר, זמן אמת יגיע דרך שרת שלנו, ועוברים למנוע מסלולים קיים.

## 1. עקרונות
- Android native או Kotlin Multiplatform אינם נדרשים בשלב הראשון; מומלץ להתחיל ב־Android native עם Kotlin אם אין סיבה עסקית אחרת.
- הפרדה ברורה בין UI, מודל תחבורה, מנוע מסלולים, התאמה אישית ושכבת נתונים.
- ספקי נתונים מאחורי ממשקים פנימיים, כדי שניתן יהיה להחליף ספק.
- אין לקשור את לוגיקת המסלולים ישירות למסכי האפליקציה.
- מצב offline יטפל בהיסטוריה ובהעדפות; חיפוש עדכני עשוי לדרוש רשת.

## 2. רכיבי לקוח Android
1. **Presentation:** מסכי חיפוש, תוצאות, פרטי מסלול, העדפות והיסטוריה.
2. **Route domain:** מודלים של מסלול, מקטע, תחנה, קו וזמן.
3. **Routing engine:** בניית חלופות ודירוגן.
4. **Personalization:** פרופיל הליכה, המתנה והחלפה.
5. **Trip recorder:** תיעוד נסיעה בזמן שהאפליקציה פתוחה בלבד.
6. **Repository layer:** איחוד נתונים מספקי תחבורה, אחסון מקומי ושרת.
7. **Privacy controls:** הרשאות, הסכמה, מחיקה וייצוא.

## 3. שרת אפשרי
- API מאובטח לנתוני משתמש, לחיפוש, ל־Sessions, לסיכומים ולהעדפות.
- מתווך זמן אמת: מקבל מהאפליקציה קודי תחנות או קווים, שואל את SIRI-SM של משרד התחבורה עם קוד הגישה שנשמר בשרת, ומחזיר הערכות. בלי מיקום המשתמש (`docs/REALTIME.md`).
- טכנולוגיה מוצעת באפיון: NestJS/TypeScript או מקבילה, לפי ניסיון הצוות. PostgreSQL, ו־PostGIS אם יידרשו נתונים מרחביים. Redis רק אם מדידות עומס יצדיקו אותו.
- שכבת אינטגרציה לספק נתוני תחבורה.
- מסד נתונים לנתוני תחבורה, העדפות ומדידות מאושרות.
- תהליך אנליטיקה שמסנן חריגים ומפיק סטטיסטיקות מצרפיות.
- ניטור, גיבוי ומדיניות מחיקה.

ניתן להתחיל ב־MVP ללא שרת מותאם אישית אם מקור הנתונים והדרישות מאפשרים זאת, ולשמור את הפרופיל מקומית. יש לקבל החלטה זו לפני המימוש.  
**עדכון:** זמן אמת מ־SIRI-SM דורש שרת בכל מקרה (החלטה 11). השאלה שנשארה פתוחה היא רק אם גם נתוני המשתמש יישמרו בשרת.

## 4. חישוב מסלולים

**עדכון:** לפי החלטה 14, החישוב יעבור למנוע מסלולים קיים (למשל OpenTripPlanner או MOTIS, לפי השוואה). המנוע מוחלף דרך ממשק פנימי, וההתאמה האישית, הדירוג וזמן האמת יושבים מעליו. המנוע הפשוט שבאב־הטיפוס (RAPTOR על נתוני GTFS) הוא זמני. העקרונות שבהמשך הסעיף נשארים בתוקף.

ייצוג המסלול כגרף:
- צמתים: תחנות, נקודות גישה ומעברי הליכה.
- קשתות: נסיעה, הליכה, המתנה ומעבר.
- עלות קשת: זמן צפוי בתוספת משקלי העדפה וקנסות החלפה.
- אי־ודאות: רמת ביטחון נפרדת מהזמן הצפוי.

יש להימנע מחיבור תחנות על סמך מרחק בלבד ללא מידע על מעברי הולכי רגל, כניסות, רציפים וזמני מעבר כאשר נתונים אלה זמינים.

## 5. למידה אישית
- שמירת מדידה יחד עם מקור, זמן, איכות ורמת ביטחון.
- שימוש בממוצעים משוקללים או מודל סטטיסטי פשוט בגרסה ראשונה.
- זיהוי חריגים והגבלת השפעתם.
- הפרדה בין תוצאה מתוכננת לבין מסלול שבוצע בפועל.
- הצגת התאמה אישית רק כשהיא משפרת את האומדן לפי בדיקות.

## 6. אבטחה
- HTTPS בלבד.
- ניהול מפתחות וסודות בצד שרת/מערכת build מאובטחת.
- הרשאות מינימליות.
- הגבלת גישה לנתוני מיקום.
- מחיקת נתונים לפי בקשת משתמש.
